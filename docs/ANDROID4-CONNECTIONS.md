# 安卓 4.x 连接适配：与 DiPlay-API17 的对照

OpenHC v280 的最低安装版本原本就是 API 16（安卓 4.1），但原版仍按 API 21 卡住无线启动。本实验修改按能力尝试旧热点接口，还没有在安卓 4.2.2 + 华为 Mate 70 Pro+（用户报告为鸿蒙 7.0）的实际组合上验证。

## 有线：借鉴 USB 网卡的系统适配，不替换 HiCar 的协议

- [DiPlay-API17 有线源码 `8611232`](https://github.com/hange3514/DiPlay-API17/tree/861123229e44e2325423835dc05eede0d16232f1/legacy) 在 API 17 上从原始 USB 描述符读实际备用设置号，USB 授权后用 `USBDEVFS_SETINTERFACE` 更新内核端点。参见 `LegacyUsb.kt` 和 `native/usb.c`。
- OpenHC 使用同一种系统能力，修正 v280 在安卓 4.x 上把所有备用设置号当成 `0` 的问题。安卓 5.0 及以上仍使用公开的 `UsbDeviceConnection.setInterface`。USB 授权、HiCar 握手、NCM 上的 OpenHC IPv4/TUN 数据通路保持不变；不移植 iPhone 专用的 NCM 初始化、用户态 IPv6/TCP 栈或认证。
- 两次车机 USB 授权是正常流程。第二次之后若失败，在「设置 → 诊断 → 查看连接日志」查看 `OpenHC-Wired`：是否读出带端点的备用号、是否报告 `已切至备用`、是否收到首个 NTB。原生库打不开时会附上 Android 加载器错误；内核切换失败则会报告 `errno`。
- v281 实车日志已确认 TUN 建立、USB 网卡识别到备用档 1 并读到 NTB 参数，随后卡在原生库加载。v281 的 ARMv7 库以 16 KiB 对齐的 RELRO 尾部超过了 APK 内 PT_LOAD 的 4 KiB 页范围；现在 32 位库以 4 KiB 重新链接、只依赖 libc，并在构建后检查布局。v282 实车日志已确认新库成功切到备用 1，NTB、ARP 和 IPv4 双向收发成立，车机出现过连接码；随后系统报告 USB 设备离开且应用停止运行。这不能证明物理拔线，也不能确定崩溃异常类型。
- 已排查并修正旧系统上两处明确不兼容：TCP 套接字现在用具体类型关闭（API 16～18 不实现 `Closeable`），认证 AES-GCM 使用现成 BouncyCastle 轻量级实现（不引用 API 19 才有的 `GCMParameterSpec`，保持原有报文格式与标签校验）。新包会在「查看连接日志」顶部显示最近一次未捕获的 Java/Kotlin 异常及调用栈，不记录异常原文和连接码。
- v283 已在 Android 4.2.2 + Mate 70 Pro+ 上通过首次有线连接和投屏。使用中拔线重插时，日志表明 USB 网卡、TCP 和控制握手完成后才出现认证失败；另有同一认证连接两次免码设备握手被旧逻辑拒绝的截图。
- v284 移植上游 `622e764` 的重发处理：同一设备且尚未交换认证数据，握手最多接受三次，仍按原规则验证配对与签名。车机连接日志现记载认证模式、握手重发、认证消息码和失败类型，不记录连接码或认证报文。`Peer(17)` 是手机返回的认证错误，和重复握手分别观察；不自动清除配对。
- 真机复测：覆盖安装 v284，保留手机和车机的配对记录；确认能投屏后拔线，等至少 5 秒再插回，不点「立即重试」。若失败，查看同一尝试号从「控制握手完成」到「协议会话结束」的连接日志。

## v285 有线免码认证与诊断

- v284 实车两次都接受了重发握手。车机收到 STS 开始请求 `0x0011`、回复 `0x8011`，随后手机直接发 `0x8080`（`Peer(17)`），没有发 STS 确认 `0x0012`。OpenHarmony `security_device_auth` 的公开参考（`0931384`，`sts_client.c`、`hichain.h`）在这个阶段用 17 表示签名证明校验失败；实车日志不能区分手机存错公钥、车机身份变化或厂商兼容差异。
- v285 有线、无线免码认证都要求当前车机标识有原先保存的长期密钥。只保存了手机记录并不足够；不会临时生成密钥去回连。诊断只增加已保存密钥的有无和 STS 请求方身份比对结果，不记录身份、密钥或报文。现有信任库不清空、不改格式。
- 原 v280 和本地测试包包名不同、内置身份参数相同。如果用同一车机标识交替配对，两份应用私有信任库可能保存不同车机密钥；测试中复现了该分支的 `Peer(17)`。实车复测时只启动测试包，若仍被拒绝，仅在手机 HiCar 中移除这台车机，再连接并输入新连接码。成功后再拔插验证免码回连。
- 「设置 → 诊断」和日志窗口均可清空连接日志。此操作需确认，仅清连接日志，不清崩溃记录、设置或配对；复测前清一次可减少截图范围。

## v286 应用内返回投屏与车机身份对照

- v285 实车在重新输码后能投屏，但回首页点「停止」后再拔线、等够时间重插，仍被手机拒绝免码认证。因此物理拔线时来不及发送结束消息，不是问题出现的必要条件。
- 蓝牙地址参与车机 ID；一直没有地址时用固定退化值，不会每次随机换。v286 不改变有线地址选取、车机身份或信任库；同一进程内完成一次有线输码配对后，下次连接只记录蓝牙地址来源、车机 ID 和长期公钥是否分别与上次配对相同。不能以此判断手机的实际公钥记录；无配对基准时日志会注明。
- 原版安卓 4 界面每次投屏状态刷新、或从首页回到 HiCar 时都会摘下并重加投屏视图。API 17 无法为活动的 MediaCodec 切换输出面，销毁画布有机会让静止画面一直黑着。v286 在同一次投屏中稳定挂载画布，应用首页/设置用不透明的界面层遮住它、停止回控，返回时露出同一画布；投屏结束或 Activity 销毁才释放。应用真正退到系统后台时仍遵循系统 Surface 生命周期。
- 黑屏复测：手机画面静止时，连续几次「返回 → 回到 HiCar」，不点手机投屏里的应用；检查是否直接显示，回首页时不应把触摸送给手机。若仍黑屏，查看 `OpenHC-Projection` 是否在应用内切页时报告画布销毁/重建。

### v286 真机回执与有线对照结果

- 2026-11-25，用户确认 Android 4.2.2 上应用内返回 HiCar 黑屏已修复。截图的多次「暂离 / 显示投屏页」均报告画布有效，未因这些应用内切页销毁画布。
- 有线尝试 `[3]` 于 13:59:16 完成 `PIN_PAIRING` 并进入投屏；14:00:24 按停止结束。重插的 `[4]` 使用固定退化蓝牙地址，车机 ID 和长期公钥与 `[3]` 均相同，但在 `0x0011 → 0x8011` 之后仍收到手机 `Peer(17)`。这不支持本次失败由车机 ID 漂移、车机换密钥或直接拔线独有的收尾路径引起。
- 同日实车复测：在同一 v286 的「车机蓝牙地址」手动填写后，先点「停止」再拔线和投屏中直接拔线，两种情况下重插均可免码回连。手填地址会改变线上地址和派生的车机 ID，因此本次证明新配对身份可用，不能单凭成功判定原先是占位地址本身还是手机端对应配对记录的问题。
- 有线日常使用保留此次验证有效的手填值和配对记录，不需重打包、清应用数据或继续反复配对。若填的是仅用于有线试验的本地管理地址，不当作真实蓝牙地址用于无线；无线连接没有在此次回执中验证。

## v287 有线专用地址与系统栏避让

- 有线在没有专用地址时沿用有效手填地址、再尝试系统读取。两者都没有时，为此安装生成一枚专供有线的本地管理单播地址，写入应用设置成功后才使用；以后复用，不因重启、拔插或后来读到真实地址而变。保存失败只沿用旧占位路径，不使用临时未保存地址。认证、身份资产及配对记录格式不变；新身份首次使用仍需要按手机提示配对。
- 覆盖 v286 不会自动替换已验证的手填地址。「把手填地址设为仅有线」将当前值移到有线专用项，地址不变时沿用原有有线身份；后续无线只读取真实地址的手填项或系统值。清除有线专用地址是显式操作，要确认，不清信任库。
- 全屏不再要求画到可见状态栏下；安卓 4.1～4.3 用旧窗口标志请求隐藏顶部状态栏。如果系统仍报告有遮挡，按窗口可见区避让，只补还有重叠的部分。关闭全屏时保留系统栏，对没有报告顶部的 ROM 也至少预留状态栏高度，投屏按可用区域等比缩放；沿用 v286 的投屏画布保留逻辑。系统不报告的第三方悬浮窗，应用不能在全屏时可靠识别。

## OpenHC-NG：合入 0.2.7 Android 4 底座

- 以 fork 的 `android4-support` (`34a0630`) 为底。该提交移植了上游 0.2.7 (`8132399`)，不是直接合并要求更高 minSdk 的原始 `main`。保留上游 TCP/UDP 音频协商、扩展投屏解析，以及 fork 的车机热点、日志导出和蓝牙自检；Android 最低版本仍为 API 16。
- 叠加本工作树 v287：API 16/17 USB 备用设置及原生库检查、旧系统认证和套接字兼容、有线地址持久化、投屏不重建画布、系统栏避让及诊断。车机自带热点不依赖系统的开热点隐藏接口；自动开热点才探测接口。
- 协议身份资产、签名钥库、构建产物都不提交。Gradle 通过 `OPENHC_IDENTITY_DIR` 使用本机资产，发布签名配置仍由 `OPENHC_SIGNING` 外部提供。APK 包名、签名、最低版本和覆盖关系需在打包后单独验证；组合版还需实车验证。

## 无线：热点可以参考，蓝牙传输方式不同

- [DiPlay-API17 无线 `wireless-v0.1.98`](https://github.com/hange3514/DiPlay-API17/blob/wireless-v0.1.98/docs/WIRELESS_0.1.98.md) 的实测车机是 2018 款宋 DM 的 Freescale MX9A0 / 安卓 4.2.2，使用 CM591 外置 USB 蓝牙控制器。CarPlay 的 iAP2 由应用内 USB 蓝牙栈引导，之后手机连接车机热点。实测只覆盖该车机、适配器和 iPhone 组合。
- 它用旧热点接口；该车机自动启用热点前还会等 Wi-Fi 客户端关掉，以免单射频冲突。OpenHC API 16～25 会探测旧热点接口，首次扫码认证通过后才开热点。安卓 4.x 上如果系统拒绝开热点、而车机 Wi-Fi 还开着，会提示手动关闭 Wi-Fi 客户端后重试；本修改不照搬 DiPlay 的自动关 Wi-Fi 流程，也没有切换到已手动开启的系统热点的模式。
- 这版 OpenHC 仍用 Android 系统的经典蓝牙 RFCOMM 监听。如果只看得到原厂的蓝牙音乐、电话，不能假设普通应用也能打开 RFCOMM。读不到适配器时，填 MAC、打开热点或降低版本门槛都不能替代这条蓝牙控制通道。外置 CM591 也不会自动让这版 OpenHC 工作；需要另行适配 USB 蓝牙传输、HiCar 的 SDP/RFCOMM 服务和配对，再验证 Huawei 手机。
